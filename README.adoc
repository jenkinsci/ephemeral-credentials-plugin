= Ephemeral Credentials Provider

A Jenkins plugin providing:

* `EphemeralCredentialsProvider` -- a `CredentialsProvider` that resolves
  credentials only for Pipeline builds that put something into it themselves.
  Nothing it holds is ever written to disk -- a plain in-memory map, cleared
  as soon as the owning build finishes or Jenkins restarts.
* `withEphemeralCredentials(...) { ... }` -- a global pipeline step (no
  `@Library` import needed) that, for each declared credential ID missing
  from every other store, pauses on `input` to collect it interactively,
  caches it in the provider above, and then runs its body - so an
  *unmodified* nested `withCredentials`/`checkout`/etc. inside that body just
  finds the value.

[NOTE]
.Technical note
======
This exists as a real plugin (not a JSL shared-library class), because
shared-library `src/` classes are recompiled per build - each build gets its
own `Class` object and its own copy of any `static` state, so there is no way
for such a class to act as a genuine cross-build singleton. An `@Extension`
in a real plugin, by contrast, is loaded once at Jenkins startup and is
therefore the only way to get one shared, JVM-wide instance.
======

== Usage

=== Wrapping credential consumers

[source,groovy]
----
pipeline {
    agent any
    stages {
        stage('deploy') {
            steps {
                withEphemeralCredentials([
                    ephemeralUsernamePassword(id: 'DB_ADMIN', description: 'DB admin login for this deploy'),
                    ephemeralSecretText(id: 'NEXUS_TOKEN', description: 'Nexus API token')
                ]) {
                    withCredentials([usernamePassword(credentialsId: 'DB_ADMIN', usernameVariable: 'U', passwordVariable: 'P')]) {
                        sh 'run-migration --user "$U" --password "$P"'
                    }
                    // an unmodified checkout(credentialsId: 'NEXUS_TOKEN', ...) here would also just work
                }
            }
        }
    }
}
----

If `DB_ADMIN` and `NEXUS_TOKEN` values already resolve via a "real"
credentials store (global/folder/job-scoped), nothing is prompted -- the
`withEphemeralCredentials` step checks `CredentialsProvider.findCredentialById`
first. Only a genuinely missing ID triggers `input`, guarded by a `lock` keyed
on `<runId>-<credentialId>` so parallel branches or repeated calls within
the same run (unless Jenkins gets restarted and the job goes on) don't
prompt twice.

=== Pre-warming: collecting credentials early, using them much later

`withEphemeralCredentials` doesn't require its body to do anything -- the
`for` loop that resolves/prompts/caches each declared ID runs regardless of
what the body contains, and an empty closure is perfectly valid:

[source,groovy]
----
pipeline {
    agent any
    stages {
        stage('collect ephemeral_credentials') {
            steps {
                // Nothing here needs these IDs yet - this just forces them
                // to be resolved (and, if missing, prompted for) while
                // whoever started the build is still around to answer.
                withEphemeralCredentials([
                    ephemeralUsernamePassword(id: 'DB_ADMIN', description: 'DB admin login for this deploy'),
                    ephemeralSecretText(id: 'NEXUS_TOKEN', description: 'Nexus API token')
                ]) { /* empty */ }
            }
        }
        stage('build') {
            steps {
                sh 'make all'   // takes an hour; nobody's watching by the time it's done
            }
        }
        stage('deploy') {
            steps {
                // Unmodified - DB_ADMIN/NEXUS_TOKEN are already cached from
                // the first stage, so nothing pauses here even though this
                // stage runs long after the human who started the build
                // walked away.
                withCredentials([usernamePassword(credentialsId: 'DB_ADMIN', usernameVariable: 'U', passwordVariable: 'P')]) {
                    sh 'run-migration --user "$U" --password "$P"'
                }
            }
        }
    }
}
----

This is the practical way to avoid a pipeline silently blocking on `input`
deep inside a long build, minutes or hours after whoever triggered it has
stopped watching. Here we move the (possibly interactive) credential
resolution into a cheap, early, empty-bodied call, and let everything
downstream -- wrapped or not -- just find the value already cached for
the rest of the run. It is also a manual approximation of the
`pipeline { options { ... } }` form floated earlier in this project's
design discussion (resolving declared IDs once before any stage runs),
buildable today with zero code changes here.

**Caveat worth knowing:** the cache is the in-memory JVM singleton described
below: it does not survive a controller restart, but a *paused* Pipeline
build does (that's the whole point of Pipeline's durability model). If
Jenkins restarts between the early warm-up stage and the later stage that
actually uses the credential, the build resumes correctly, but the cache is
gone: a later `withEphemeralCredentials` call for the same ID prompts again
(safe, just an extra interruption), while a later *unmodified* call relying
solely on the earlier warm-up (no `withEphemeralCredentials` at that point)
simply won't find the credential at all, since nothing at that later point
would re-trigger the interactive path. While such situations are rare,
they can be  real -- weigh it against how long the gap between warm-up
and use is, and how likely a restart is in that window. Some Jenkins
deployments deliberately disable durability in favor of performance,
and to make reasonably valid assumptions about the state of external
"systems under test" (e.g. firmware being re-flashed, etc.)

== What's here

=== `EphemeralCredentialsProvider`

The `@Extension`-registered `CredentialsProvider`.
Holds a `Map<runExternalizableId, Map<credentialsId, Credentials>>` in memory
with disabled serialization, so that sensitive credentials can be contained.

Its `getCredentialsInItemGroup(...)` (the method Jenkins' generic credentials
lookup actually calls in this plugin version -- see "API surface" below)
tries to resolve *which build is asking* via
`CpsThread.current().getExecution().getOwner().getExecutable()`
(`CpsRuns.current()`).

[NOTE]
.Technical note
======
This does not look up the build via `hudson.model.Executor` -- an `Executor`
is a transient, per-`node`-block resource that changes across parallel
branches and sequential stages/agents, whereas a `CpsFlowExecution` is
anchored to the whole build's lifetime and shared by every branch of a
`parallel` block.
======

**Discovered limitation, not just a caveat:** that resolution only works
when the caller is itself CPS-interpreted code (such as our own
`WithEphemeralCredentials.groovy` resource, or a shared-library script,
or the Jenkinsfile pipeline script itself). It does **not** work when the
caller is a step's own internal Java implementation running off the CPS
interpreter thread entirely. This was confirmed empirically against a real
embedded Jenkins in `WithEphemeralCredentialsTest`: `credentials-binding`
plugin's `withCredentials` performs its own `findCredentialById` call from
such a thread, where `CpsThread.current()` is `null`. When that happens,
the provider falls back to considering *every* run's cache and lets the
caller's own by-ID filtering pick the right entry. That's correct as long
as two different runs aren't concurrently caching different values under
the exact same literal credential ID at the same time -- which is a real,
narrow residual risk you should weigh against how likely concurrent builds
of the same job are for whatever pipeline uses this, not a merely
theoretical one. If this bites you in practice, and you know that certain
credentials used by your job would never be persistently configured,
consider using `String` variables to pass the credential names and salt
these names with a random string or something like `${env.BUILD_ID}` manually.

=== `EphemeralCredentialsRunListener`

Handles `onFinalized`/`onDeleted` cleanup. This is the authoritative cleanup
path, not a `finally` block in the pipeline script, since a hard-killed build
can skip the latter.

=== `withEphemeralCredentials` step (`WithEphemeralCredentials.groovy` + `WithEphemeralCredentialsGlobalVariable`)

Registered via the `GlobalVariable` extension point, the same mechanism that
makes `env`/`params`/`currentBuild` available without an import. The actual
logic ships as a `.groovy` **resource** file (not precompiled Java/Groovy) and
is parsed on demand through the calling script's own `GroovyClassLoader` --
the same technique `docker-workflow-plugin`'s `DockerDSL` uses for its
`Docker.groovy` for example -- so it goes through the same CPS transformation
as a shared-library script, which is what makes its calls to `lock` and `input`
steps provided by the pipeline script context safe.

Two non-obvious things that took several iterations against a real embedded
Jenkins to get right, both worth knowing before touching this file:

* **The calling build's own sandbox status applies to this code too.**
  Since it's compiled through the *calling* script's classloader, a
  sandboxed Jenkinsfile makes this code sandboxed as well -- every non-step
  Java call it makes (even into this plugin's own classes) needs an entry in
  `whitelist.txt` (loaded by `EphemeralCredentialsWhitelist`), or it's
  rejected with `RejectedAccessException`, the same way `credentials-binding`
  and `docker-workflow-plugin` ship their own whitelists. This includes
  things that look like "obviously fine" Jenkins core calls --
  `currentBuild.rawBuild` itself was rejected during development.
* **Never hold a live `Run` (or this plugin's own singleton) across a
  `lock`/`input` pause.** This class sits in the script's binding for the
  whole build, so CPS's own program-state serialization walks it every time
  the pipeline pauses. `WorkflowRun` isn't Java-serializable, so an earlier
  version that stored a `Run` field failed with `NotSerializableException`
  the moment `input()` paused. The fix: store only the plain
  `externalizableId` String, and re-resolve `Run.fromExternalizableId(...)`
  fresh right before each synchronous use, never held across a pause.

=== Credential type factories

All five credential types the standard "Add Credentials" UI offers are
wrapped, each its own `GlobalVariable` returning a precompiled
`groovy.lang.Closure` that builds the matching `EphemeralCredentialSpec`
subclass:

[cols="1,2,3"]
|===
|Factory |Spec class |Materializes

|`ephemeralUsernamePassword(id:, description:)`
|`EphemeralUsernamePassword`
|`UsernamePasswordCredentialsImpl`

|`ephemeralSecretText(id:, description:)`
|`EphemeralSecretText`
|`StringCredentialsImpl`

|`ephemeralSSHUserPrivateKey(id:, description:)`
|`EphemeralSSHUserPrivateKey`
|`BasicSSHUserPrivateKey` (optional dependency -- see below)

|`ephemeralSecretFile(id:, description:, fileName:)`
|`EphemeralSecretFile`
|`FileCredentialsImpl`

|`ephemeralCertificate(id:, description:)`
|`EphemeralCertificate`
|`CertificateCredentialsImpl`
|===

Every `EphemeralCredentialSpec` carries:

* an `id`,
* a `description` passed straight through to `input` step's `message`,
* the `input` `ParameterDefinition` items to collect, and
* the logic to turn the answers into a `Credentials` object.

Since these factories never invoke a pipeline step themselves, a plain
precompiled `Closure` is fine for them -- no CPS transformation, no
whitelist entries needed (unlike `WithEphemeralCredentials.groovy` itself).

**Secret file and certificate collect their content as pasted base64 text,
not a real file upload.** The `input` step's `FileParameterDefinition` writes
the uploaded file to disk as part of its own normal handling -- in direct
tension with this plugin's "never persisted" design -- so both specs ask
for base64-encoded text instead (the file's raw bytes / the PKCS#12
keystore's raw bytes, base64-encoded) and decode it entirely in memory via
`SecretBytes.fromBytes(...)`. A pragmatic simplification, not a
faithful reproduction of the web UI's upload widget.

**`ephemeralSSHUserPrivateKey` has a soft dependency on the "SSH
Credentials" plugin** (https://plugins.jenkins.io/ssh-credentials/) -
unlike the other four types, which only need plugins this one already
requires unconditionally. It's declared `<optional>true</optional>` in
`pom.xml`, so an installation that never uses this specific credential
type doesn't need SSH Credentials installed at all - the manifest records
it as `resolution:=optional`. Constructor of `EphemeralSSHUserPrivateKey`
deliberately touches `BasicSSHUserPrivateKey.class` (a class literal is
enough to force resolution) so a missing plugin fails immediately, with a
clear message, at the point the pipeline author declares the spec - not
deep inside `materialize()` after a human has already answered an `input`
prompt for nothing.

Adding another credential type (e.g. for GitLab or GitHub API tokens,
other SSH and certificate types) means one more `EphemeralCredentialSpec`
subclass plus one more tiny factory `GlobalVariable`, following the same
shape.

=== Extending with more types: doesn't require changing this plugin

`EphemeralCredentialSpec.inputParameters()`/`materialize()` never invoke a
pipeline step: they are pure data/logic building a `ParameterDefinition`
list and a `Credentials` object -- so a new spec subclass has none of the
CPS/sandbox constraints `WithEphemeralCredentials.groovy` itself has.

Three places a new type can live:

* **This plugin**: add the subclass + factory `GlobalVariable` here, cut a
  new release. Right choice for something broadly useful, like the five
  standard types above.
* **A separate plugin**: depend on `ephemeral-credentials-provider`,
  define your own subclass + `GlobalVariable`. Only *needed* for the
  factory/DSL-registration half, since `GlobalVariable` is a genuine
  `ExtensionPoint` requiring `@Extension` discovery at Jenkins startup,
  which only a real installed plugin gets.
* **JSL - no new plugin at all.** The spec subclass can be an ordinary JSL
  `src/` class extending this plugin's `public abstract class
  EphemeralCredentialSpec` (its constructor is `protected`, so any
  subclass anywhere can call `super(id, description)`). Many JSL's already
  reference classes from other installed plugins directly today (e.g.
  `CredentialNotFoundException` from `credentials-binding`), this is the
  same pattern. The factory doesn't need `GlobalVariable` either: a plain
  `vars/ephemeralXyz.groovy` with `def call(Map args) { new
  EphemeralXyzSpec(args.id, args.description) }` becomes callable exactly
  the way `usernamePassword(...)` reads, because JSL `vars/` files *are*
  the native mechanism of Jenkins for contributing global callables -- no
  explicit `@Extension`, no plugin install, just a file in the library.

So a plugin release is only strictly required for the `GlobalVariable`
registration step -- anything that's pure data (every implementation of
an `EphemeralCredentialSpec` so far) can live in a JSL instead, with zero
coordination against this plugin's release cycle.

== Tests

`WithEphemeralCredentialsTest` runs real declarative pipelines against an
embedded Jenkins (`JenkinsRule`, JUnit 5 `@WithJenkins`):

* `alreadyRegisteredCredentialIsNeverPrompted`: an ID already resolvable via
  `SystemCredentialsProvider` is used as-is; no `input` ever appears.
* `missingCredentialPromptsAndReusesCacheOnSecondCall`: a genuinely missing
  ID pauses on `input` (submitted programmatically via
  `InputStepExecution.proceed(Map)`), the submitted value reaches an
  unmodified nested `withCredentials`, and a second `withEphemeralCredentials`
  call for the same ID in the same run reuses the cache instead of pausing
  again -- as does a *third*, completely unwrapped `withCredentials` call
  later in the same run, confirming the cache is genuinely visible to
  code that never calls `withEphemeralCredentials` at all.
* `sshKeySecretFileAndCertificateMaterializeCorrectly`: all three of the
  newer credential types (initial support/PoC focused on `EphemeralSecretText`
  and `EphemeralUsernamePassword`), resolved in one `withEphemeralCredentials`
  block (three sequential `input` pauses), each consumed through its standard
  `withCredentials` binding (`sshUserPrivateKey`/`file`/`certificate`)
  inside the same pipeline run -- not by querying
  `EphemeralCredentialsProvider` after the build finishes, since
  `EphemeralCredentialsRunListener` clears the cache for a run as soon as
  it's done, so nothing would be left to find by then.

The `ssh-credentials` plugin is present on this project's own test classpath
(it is a normal, if `optional`, compile dependency of this plugin: `optional`
only affects whether it propagates to consumers of *this* artifact, not
whether it's available here), so the "plugin genuinely absent" code path for
`ephemeralSSHUserPrivateKey` isn't exercised by an automated test -- that
guarantee rests on the well-understood JVM behavior described above
(a class literal inside a method is resolved when that method runs, not
when the enclosing class loads), rather than on a harness rigged to remove
an already-declared dependency.

`WithEphemeralCredentialsCustomLibraryTest` illustrates and confirms that a
*completely custom* credential type can be added without touching this
plugin at all - by defining an `EphemeralCredentialSpec` subclass and its
factory function in an ordinary (trusted, global) shared library instead,
per the "Extending with more types" section above. The library content
lives as genuine `.groovy` resource files under
`src/test/resources/com/myprovys/ci/credentials/{vars,src}/` (not embedded
Java string literals), copied into a throwaway local git repo
(`GitSampleRepoRule`) and loaded via `GlobalLibraries`/`SCMSourceRetriever`/
`GitSCMSource` - the same mechanism a real Jenkins controller uses for a
globally-configured library, and the exact pattern the shared-library
plugin's own test suite (`GlobalLibrariesTest`) uses to test this feature.
The example library defines `vars/myCorpApiToken.groovy` (an
independently-named factory, parallel to this plugin's own
`ephemeralSecretText`) and `src/com/example/jsl/MyCorpApiTokenSpec.groovy`
(an independently-named spec subclass reusing `StringCredentialsImpl` -
the same type `EphemeralSecretText` already wraps - purely to prove the
extension mechanism, not to add a genuinely new credential type).

This test is deliberately classic JUnit 4 (`@Rule`, `org.junit.Test`)
rather than this project's usual JUnit 5 `@WithJenkins`, since
`GitSampleRepoRule` - the standard way to test SCM-loaded shared libraries -
is itself a classic JUnit 4 `@Rule`; `junit-vintage-engine` lets our
JUnit-Platform-based surefire run it alongside the rest. Two things worth
knowing if this test needs touching:

* **`JenkinsRule.timeout` needed raising to 600s.** This test's extra
  plugin set (`git`, `scm-api`, `pipeline-groovy-lib`, and their own
  transitive dependencies) makes plugin discovery alone slower than
  `JenkinsRule`'s 180-second default in this environment - confirmed by a
  thread dump showing the boot still stuck in plugin discovery at the
  180-second mark, nowhere near the actual test logic yet.
* **`git` needed a `ephemeral_credentials` version bump.** `git` 5.5.2 refused to
  load against the `ephemeral_credentials` version this project's BOM snapshot
  otherwise provides (`1371.vfee6b_095f0a_3`), demanding
  `1378.v81ef4269d764` or higher - resolved with a `dependencyManagement`
  override for just that one artifact (see the Build section) rather than
  moving the whole BOM, since `1378` is a version already known to compile
  clean against this project's code (it was the very first pin this
  project used, before switching to BOM management).

A non-blocking warning also surfaced during this work, worth watching:
`workflow-cps` logs (but does not yet enforce) a
`GroovySourceFileAllowlist` check against loading
`WithEphemeralCredentials.groovy` "without sandbox protection" the way
`WithEphemeralCredentialsGlobalVariable` does (`getResourceAsStream(...)` +
`parseClass(...)`, described above). The build still succeeds today, but
the warning message describes an opt-in allowlist system
(`GroovySourceFileAllowlist.DefaultAllowlist.ALLOWED_SOURCE_FILES`) that a
future `workflow-cps` release could plausibly tighten from warn to enforce -
worth re-checking if this plugin's `workflow-cps` dependency is ever
bumped.

Run with `mvn test`.

== Build

Standard Jenkins plugin Maven build, via the `org.jenkins-ci.plugins:plugin`
parent POM:

[source,shell]
----
mvn package
----

Produces `target/ephemeral-credentials-provider.hpi`.

`mvn verify` additionally requires a clean `spotbugs:check` and
`spotless:check` (both bound to the `verify` phase). SpotBugs comes from
the parent POM unconditionally; Spotless is already fully configured
there too (Palantir Java Format for `.java`, `sortPom` for `pom.xml`) but
ships **off** by default behind `spotless.check.skip` - this project
overrides that property to `false` rather than declaring a second,
separate `spotless-maven-plugin` block (which would just duplicate the
inherited one, and risks configuring the wrong formatter - an earlier,
wrong attempt at this pinned `googleJavaFormat` instead of the
`palantirJavaFormat` the parent actually uses, and would have run as a
second, redundant execution). Fix formatting issues with `mvn
spotless:apply`.

Dependency versions in `pom.xml` target the core version JSL currently
targets (`jslcus/resources/core-version.txt` = `2.462.3`, set as the
`jenkins.version` property). Most plugin versions come from importing
`io.jenkins.tools.bom:bom-2.462.x` (a mutually-consistent set for this exact
core line).

[NOTE]
.Technical note
======
Resolving `workflow-cps`/`pipeline-input-step`/`lockable-resources` plugins'
differing transitive wants piecemeal repeatedly hit the parent POM's
`RequireUpperBoundDeps` enforcer rule during development; importing the
common Jenkins BOM was much less fragile than pinning each conflict by hand
as it surfaced). The `lockable-resources` (`org.6wind.jenkins`, a community
plugin outside that BOM) and `jenkins-test-harness` (pinned via the
`jenkins-test-harness.version` property the parent POM requires) are
pinned directly, matching what other projects already verified for this
same core baseline.
======

Re-audited 2026-07 against a later BOM snapshot, to check whether any of
the manual pins below had since become redundant:

* `pipeline-model-declarative-agent`: still not covered, even by the
  latest `bom-2.462.x` snapshot available at the time
  (`4228.v0a_71308d905b_`) -- a small, rarely-updated plugin that appears to
  have never been added to BOM coverage. Still pinned by hand.
* `jenkins-test-harness.version`: still genuinely required. Dropping the
  override and letting the parent POM's own default apply
  (`2573.vd91b_8a_43e019` at the time of checking) reproduces the exact
  `NoSuchMethodError` this override was originally added to fix -- the
  parent POM's default doesn't track `jenkins.version` above.
* Bumping the BOM itself to that latest snapshot was tried and reverted --
  it pulls in a newer `ephemeral_credentials` plugin whose
  `UsernamePasswordCredentialsImpl` constructor now declares
  `throws FormException`, a breaking change for `EphemeralUsernamePassword`.
  Not worth adopting for no gain, since it still doesn't cover the
  `pipeline-model-declarative-agent` either way.
* `lockable-resources` remains a community plugin (`org.6wind.jenkins`)
  and was never a candidate for BOM coverage.

**`FormException` fixed defensively, without adopting the newer BOM.**
`EphemeralUsernamePassword.materialize()` now wraps the
`UsernamePasswordCredentialsImpl` constructor call in
`try { ... } catch (Exception e) { throw new IllegalStateException(...); }`
- catching the broad `Exception` type rather than importing and naming
`Descriptor.FormException` specifically. That's the point: Java only lets
you catch a checked exception a `try` block could plausibly throw, and our
*current* `ephemeral_credentials` plugin version doesn't declare `FormException` on
this constructor at all, so naming it would fail to compile today. `Exception`
is always a legal catch clause regardless of what the currently-resolved
dependency version declares, so this same code compiles unchanged against
both the version we ship against now and a future one that does throw
`FormException` - confirmed by temporarily bumping the BOM to its latest
snapshot and compiling against both, then reverting. The other four
credential-type constructors compiled clean under that newer snapshot too -
only picked up deprecation warnings (a superseded `PasswordParameterDefinition`
constructor; `SecretBytes.fromBytes`/`UploadedKeyStoreSource(SecretBytes)`
in `EphemeralCertificate`/`EphemeralSecretFile`), not compile errors, so
they're left alone for now - worth revisiting if this project's core
baseline ever actually moves forward.

The `lockable-resources` and `pipeline-input-step` plugins are declared as
real (non-test) dependencies, even though no Java code here imports their
classes -- the `WithEphemeralCredentials.groovy` calls their `lock`/`input`
steps by name, and declaring them here is what makes maven-hpi-plugin
record them as required plugin dependencies in the manifest, so an ultimate
Jenkins controller would refuse to load this plugin without them installed.

Note on API surface: this version of `credentials-plugin` does not declare
`getCredentials(...)` as abstract -- it's kept only as a deprecated
compatibility shim. The real extension point subclasses must override is
`getCredentialsInItemGroup(Class, ItemGroup, org.springframework.security
.core.Authentication, List<DomainRequirement>)`, which is what this plugin
does. Confirmed by decompiling the resolved plugin jar during development;
worth re-checking if the `ephemeral_credentials` dependency version is ever bumped.

`git` (needed only as a test dependency, for `WithEphemeralCredentialsCustomLibraryTest`)
required bumping `ephemeral_credentials` past what this project's BOM snapshot
otherwise provides - see the test's own notes above. Pinned via a
`dependencyManagement` override for just that one artifact rather than
moving the whole BOM:

[source,xml]
----
<dependency>
    <groupId>org.jenkins-ci.plugins</groupId>
    <artifactId>credentials</artifactId>
    <version>1378.v81ef4269d764</version>
</dependency>
----
